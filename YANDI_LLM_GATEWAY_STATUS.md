================================================================================
Дата: 2026-09-11

================================================================================
1. ЗАЧЕМ ЭТО ВООБЩЕ НУЖНО
================================================================================

YANDI — сеть добровольных, самостоятельных узлов, а не сервис с
"пользователями" на одном общем сервере. У каждого держателя ноды —
своё железо: у кого-то мощный сервер, у кого-то ноутбук, у кого-то
телефон. Модель, которую нода использует, должна быть выбором её
владельца, а не жёстко зашитым в код Ollama-инстансом.

Отсюда мандат: любая нода подключает ЛЮБУЮ модель — локальный файл на
любом диске, свой удалённый API (включая собственный доступ к Клоду
через нативный Anthropic API), или любой self-hosted сервер с
OpenAI-совместимым протоколом. Какая именно модель стоит на ноде —
неважно для сети (см. отдельную память про "нода = нейрон, важны
связи, а не начинка"); важно, чтобы КАЖДАЯ нода могла выбрать своё.

================================================================================
2. ЧТО УЖЕ СДЕЛАНО — ОБВЯЗКА (llm_gateway/)
================================================================================

Раньше ~29 файлов в agent/ сами били HTTP-запросами напрямую в Ollama,
каждый со своей копией адреса и своим разбором ответа. Теперь всё это
— один пакет, одна точка входа.

Состав:
- `client.py` — единственная функция `complete()`, которую вызывает
  весь agent/. Сама решает, каким движком отвечать; вызывающий код
  этого не знает и не должен знать.
- `llamacpp_backend.py` — свой движок инференса (llama.cpp), те же
  GGUF-веса, что раньше качались под Ollama, но БЕЗ HTTP-сервера
  Ollama между нами и моделью.
- `remote_backend.py` — два реальных протокола: OpenAI-совместимый
  (`/chat/completions`) и нативный Anthropic Messages API
  (`/v1/messages`, свои заголовки, свой формат ответа). Через это нода
  подключает свой собственный доступ к Клоду или к самостоятельно
  поднятому серверу.
- `setup.py` — интерактивная настройка при первом запуске: указать
  папку с файлом модели на диске, ИЛИ ввести адрес/протокол удалённого
  сервера. Никогда не переписывает существующую запись молча — только
  явное "удалить и настроить заново".
- `config.py` — тонкая точка входа поверх реального хранилища
  (`secure_store.py`, см. ниже), чтобы смена формата хранения никогда
  не требовала трогать вызывающий код.

Порядок выбора движка внутри `complete()` (в этом порядке, каждый шаг
опционален):
  1. Собственная настройка ЭТОЙ ноды для точного имени модели (если
     владелец её настроил — она всегда побеждает, явный выбор сильнее
     любого дефолта).
  2. Встроенный дефолт — свой движок llama.cpp с тем файлом модели,
     что уже реально стоит на этой машине.
  3. Ollama по HTTP — фоллбэк, если ни своя настройка, ни встроенный
     движок не сработали.

Свой движок включается через `LLM_GATEWAY_ENABLE_LOCAL=1` (уже стоит в
`start.sh`/`start_headless.sh`) — специально ВКЛЮЧЕНИЕМ, а не
выключением: десятки существующих regression-тестов в agent/ до сих
пор мокают прямой HTTP к Ollama по именам моделей, и включение по
умолчанию тихо сломало бы эти тесты, подсунув им настоящую 10-гигабайтную
модель вместо мока.

3. ЧТО СДЕЛАНО ПОСЛЕ — ШИФРОВАНИЕ НАСТРОЕК (secure_store.py)
================================================================================

Настройки модели узла (пути к файлам, адреса серверов) хранятся не в
обычном файле, а в локальной базе с реальными гарантиями, проверенными
атаками, а не просто "заявленными":

- Ключ шифрования (KEK) генерируется кодом сам (случайные байты),
  один раз, автоматически — ни владелец, ни кто-либо ещё его не
  выбирает и не вводит руками.
- Имя модели ТОЖЕ зашифровано, не только сама настройка — вместо
  "heretic:q8" в файле базы лежит непрозрачный отпечаток (HMAC) плюс
  зашифрованная копия для отображения. У файла базы без ключа нельзя
  узнать даже список того, что настроено.
- "Изменить" не существует как операция — только вставить или
  удалить. Подмена одного байта в зашифрованной записи ломает
  расшифровку, а не тихо принимается.
- Отдельный неизменяемый журнал (append-only, с цепочкой HMAC) — и,
  что важнее, ФАКТИЧЕСКОЕ содержимое базы каждый раз сверяется с тем,
  что журнал утверждает должно быть живо. Строку нельзя ни вставить,
  ни удалить в обход журнала незамеченно — расхождение ловится ДО
  расшифровки и выдачи данных наружу.
- Последняя доверенная точка журнала хранится ОТДЕЛЬНЫМ файлом рядом
  с ключом — подмена файла базы целиком более старой копией
  обнаруживается при следующем открытии.
- `harden_key.sh` — разовый шаг с root (`chattr +i`), после которого
  файл ключа не может быть изменён или удалён вообще никем, включая
  root, без отдельного намеренного снятия защиты.

Проверено не на словах: несколько раундов адверсариальных атак
(порча байт, обход журнала через сырой SQL, откат файла базы, гонки,
кросс-базовая инъекция, крах между записью и чекпоинтом) — 105
regression-тестов, все зелёные. Честно зафиксированные пределы, которые
НЕ лечатся кодом: (1) синхронный откат сразу всех трёх опор (база +
журнал + чекпоинт) одной машиной не отличить от легитимного состояния
— нужен внешний свидетель, сеть нод, это будущая работа; (2) кто владеет
самим ключом — тот и есть легитимная нода, это математика любой
MAC/AEAD-схемы, не дыра; (3) root/владелец файла физически может
прочитать сырые байты ключа — программно не лечится, нужно другое
железо (TPM/HSM), не строили.

================================================================================
4. К ЧЕМУ СТРЕМИМСЯ ДАЛЬШЕ
================================================================================

- Полная отвязка от Ollama: сейчас Ollama — рабочий фоллбэк, цель —
  чтобы он стал полностью необязательным, а не тем, на что многое до
  сих пор тихо опирается.
- Привязка настройки модели узла к настоящей криптографической
  идентичности ноды (`node/src/core/identity.rs` — реальные
  Ed25519/X25519 ключи, из которых уже выводится виртуальный IPv6) —
  сейчас это два не связанных друг с другом мира: обвязка модели живёт
  в `llm_gateway`, идентичность узла — в транспортном слое на Rust.
  Не начато, не заявлено как следующий шаг без отдельного мандата.
- Внешний сетевой свидетель для защиты от синхронного отката сразу
  всех локальных опор (см. предел выше) — осознанно отложено, требует
  сначала эпистемики доверия между нодами (отдельная, ещё не начатая
  работа, см. память про "нода = нейрон, связи = навык сети").

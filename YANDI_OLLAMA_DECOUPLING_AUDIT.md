================================================================================
1. EXECUTIVE SUMMARY
================================================================================

Коротко: `llm_gateway` — реальный, хорошо построенный шлюз, и ВНУТРИ
`agent/` он честно работает как единственная точка входа для генерации
текста. Но это только один из трёх миров кода в проекте, и остальные
два (`pet/` — веб-чат, `node/` — P2P-транспорт) о шлюзе не знают вообще.
Плюс внутри самого `agent/` есть целый КЛАСС вызовов (эмбеддинги),
который шлюз никогда не покрывал. Плюс даже там, где шлюз используется
правильно, найден воспроизводимый путь, где явный выбор владельца ноды
может быть тихо подменён на Ollama при сбое.

Подсчёт находок (по кластерам, не по отдельным строкам):

- Кластеров с LIVE_BYPASS (обход шлюза в живом коде): **3**
  1. `pet/` — весь веб-чат (6 файлов), ноль импортов llm_gateway.
  2. `node/src/ai_rpc/*` (Rust, 6 файлов) — P2P AI-инференс для пиров,
     на 100% захардкожен на Ollama, мост со шлюзом физически невозможен
     (Rust ↔ Python).
  3. `agent/` эмбеддинги (минимум 3-8 файлов, точное число требует
     отдельной сверки — см. §2.3) — целый класс вызовов, который
     `llm_gateway` никогда не абстрагировал.
- Отдельная, не менее важная находка — **не bypass, а дефект внутри
  самого шлюза**: тихий откат на Ollama при сбое ЯВНО настроенного
  владельцем backend'а (см. §5). Это происходит ЧЕРЕЗ шлюз, не в обход
  него, поэтому не считается в LIVE_BYPASS, но нарушает тот же принцип
  ("явный выбор побеждает").
- Ещё одна архитектурная дыра внутри шлюза: кросс-нодовая валидация
  требует, чтобы ЧУЖАЯ нода говорила именно на Ollama-протоколе (см. §5).
- LIVE_CRITICAL (без шлюза вообще, без фоллбэка): 0 в `agent/` для
  генерации текста; но эмбеддинги в `agent/` де-факто LIVE_CRITICAL для
  функций, которые их используют (нет никакого фоллбэка вообще).
- LIVE_FALLBACK (корректный, спроектированный путь): `start.sh`'s
  health-check (warn, не блокирует) и сам путь Ollama внутри
  `llm_gateway.client.py` для generation — оба по конструкции корректны.
- DEAD_OR_LEGACY: 4 файла/кластера в `agent/` (`orchestrator.py` целиком,
  `daemon.py` целиком, `council_analyzer`-кластер, `orch_federation.py`'s
  `LocalOllamaDriver`) — физически недостижимы, миграция не нужна,
  нужно решение "удалить или оставить как груз".
- TEST_ONLY: ~15+ тестовых файлов в `agent/` (исторические метки/моки),
  плюс все 5 тестовых файлов `llm_gateway/` — но последние ПРОВЕРЯЮТ
  реальное поведение, не исторический мусор (см. §3).
- UNCERTAIN: 3 места в `agent/` (см. §2.4), требуют отдельного прохода.

**Можно ли сегодня честно сказать "YANDI работает без Ollama"? Нет.**
Причины, по фактам, не по ощущению:
(а) реальный веб-интерфейс, которым пользуется человек (`pet/`), имеет
несколько живых функций, тихо деградирующих без Ollama, и ни одна из
них не проведена через шлюз;
(б) P2P-транспорт (`node/`) имеет живую фичу "поделиться интеллектом с
сетью", на 100% зависящую от Ollama;
(в) даже внутри `agent/`, где шлюз реально работает для генерации,
эмбеддинги — это отдельный, никогда не абстрагированный класс вызовов,
и ключевые эпистемические функции (`claim_relation.py` — определение
противоречий между утверждениями) падают без Ollama напрямую;
(г) даже там, где шлюз используется правильно, явный выбор владельца
ноды может быть тихо подменён при сбое (см. §5) — то есть сам инвариант
"явный выбор побеждает" сегодня не выполняется на 100% даже в
"образцовой" части кода.

5. LLM_GATEWAY REVIEW
================================================================================

Фактический порядок выбора backend в `client.py::_do_complete` (строки
165-216, подтверждено построчным чтением, не по докстрингу):
1. `_try_configured_backend()` — настройка владельца узла для точного
   имени модели (строка 191) — читается через `config.py`/`secure_store.py`,
   старого пути в обход не найдено.
2. Встроенный реестр llama.cpp (строка 198).
3. Ollama по HTTP (строки 207-212) — **только когда
   `_LOCAL_ENABLED and base_url == DEFAULT_BASE_URL`** (строка 189).

Утечки абстракции в `agent/` не найдено: 23 файла импортируют
`llm_complete`, ни одного `if backend == "ollama"` в живом коде.
`remote_backend.py` подтверждённо независим от Ollama (не импортирует
`requests`... то есть импортирует, но никаких Ollama-specific
допущений); Anthropic-ветка бьёт в реальный нативный `/v1/messages` с
правильными заголовками, не притворяется через OpenAI-формат.
`llamacpp_backend.py` вообще не знает про HTTP/порт 11434 ни при каких
условиях.

**КРИТИЧЕСКАЯ НАХОДКА — тихий откат на Ollama вопреки явному выбору
владельца ноды СУЩЕСТВУЕТ, и это не баг по недосмотру, а закреплённый
тестом контракт.**

```python
# client.py:189-206 (упрощённо)
if _LOCAL_ENABLED and base_url == DEFAULT_BASE_URL:
    try:
        result = _try_configured_backend(...)   # <- ЛЮБАЯ явная настройка владельца
        ...
    except Exception as e:
        print(f"...локальный движок не справился с {model!r} ({e}), откат на Ollama")
if text is None:
    text, raw = _do_complete_ollama(...)
```

`except Exception` ловит АБСОЛЮТНО ЛЮБОЙ сбой внутри
`_try_configured_backend()` — не только "встроенный дефолт не сработал",
но и: (а) реальный сетевой сбой у явно настроенного REMOTE backend'а
(например, у собственного ключа Anthropic кончился лимит), (б) битую
конфигурацию (`RuntimeError("неизвестный backend ...")`). В обоих
случаях код МОЛЧА подставляет Ollama вместо явной ошибки конфигурации.

Живой воспроизведённый сценарий (Scenario D третьего аудита): владелец
явно настроил remote backend, именно этот сервер недоступен → лог
показал `"...откат на Ollama"`, Ollama РЕАЛЬНО была вызвана. В этом
конкретном прогоне финальный вызов всё же упал с ошибкой только потому,
что мок-ответ Ollama был в чужом формате — если бы настоящая Ollama на
машине ответила в СВОЁМ формате (как она и делает в реальности), вызов
вернул бы **успешный текст от другой модели**, и единственным следом
подмены остался бы `print()` в stdout, который вызывающий код (`agent/`)
не проверяет и не видит.

Это поведение **явно, намеренно протестировано** в
`client_regression_test.py:240-248` и `:304-310` — то есть его нельзя
"просто убрать одной правкой", не тронув и тест.

**Ответ на главный вопрос мандата: B.** Путь существует, воспроизводим
эмпирически, закреплён тестом.

**Отдельная архитектурная дыра, найденная попутно: кросс-нодовая
валидация требует Ollama-протокол у ЧУЖОЙ ноды.** `orch_validator.py`
вызывает `llm_complete(..., base_url=endpoint_другой_ноды, ...)`. В
`client.py` условие на строке 189 (`base_url == DEFAULT_BASE_URL`)
означает: любой ДРУГОЙ `base_url` идёт напрямую в Ollama-путь
безусловно. Значит, чтобы одна нода могла проверить другую, у ЧУЖОЙ
ноды должен быть запущен именно Ollama-совместимый `/api/chat` на
порту 11434 — нода, у которой настроен только llama.cpp или только
remote Anthropic (без Ollama вообще), **не может быть опрошена другими
нодами через этот путь**. Это прямое противоречие мандату "любая
нода — любая модель" на уровне межнодового доверия, а не bypass
вызывающего кода (сам `orch_validator.py` вызывает `llm_complete`
правильно) — это ограничение самого шлюза для удалённых нод.

================================================================================
6. NO-OLLAMA SCENARIO
================================================================================

Прогнано безопасно (mock/env-изоляция, без реального удаления Ollama):

- **Нода настроена на llama.cpp через secure_store** → работает
  полностью, Ollama не участвует. Подтверждено живым GGUF-файлом.
- **Нода настроена на remote OpenAI-совместимый backend** → работает
  полностью через мок удалённого сервера, Ollama не участвует.
- **Ничего не настроено, имени нет во встроенном реестре** → корректно
  пытается Ollama, ловит `ConnectionError`, поднимает понятный `LLMError`.
  Правильное поведение.
- **Владелец явно настроил remote backend, но именно этот сервер
  недоступен** → см. §5 — тихий откат на Ollama, реально вызывает её.

Помимо `agent/` (генерация текста через шлюз работает без Ollama при
явной настройке) — при полном удалении Ollama с машины:
- `pet/` (реальный веб-чат, которым пользуется человек) — сервер
  ЗАПУСТИТСЯ, но перевод, приватный чат "Помощник", фоновая валидация и
  чистка мета-нарративов Совета — все тихо деградируют или возвращают
  ошибку конкретного эндпоинта. Ничего не падает целиком, но заметная
  часть функциональности молча перестаёт работать.
- `node/` — узел ЗАПУСТИТСЯ нормально (проверка Ollama не блокирует
  старт), но фича "поделиться интеллектом с сетью" через AI-RPC не
  будет работать ни при каких условиях — первый запрос от пира вернёт
  ошибку.
- `agent/` эмбеддинги (`claim_relation.py`, `orch_registry_search.py`,
  `final_claim_coverage.py`) — сломаются НАПРЯМУЮ, в обход шлюза, без
  какого-либо фоллбэка. Определение противоречий между утверждениями
  (ключевая эпистемическая функция) перестанет работать.
- `start.sh`/`start_headless.sh` — запустят ноду в любом случае.

7. MIGRATION MAP (ТОЛЬКО ПЛАН, БЕЗ ПРАВОК)
================================================================================

**PHASE 1 — простые прямые bypass → `llm_gateway.complete()`**
Кандидаты: `pet/chat_translate.py`, `pet/chat_orch.py::_local_validate()`,
`pet/council_claude_auto.py::_filter_reply()`, `pet/council_chat_server.py`'s
перевод/тег-утилиты. Все — одиночные text-completion вызовы без
стриминга, формат ответа простой.
Риск регрессии: низкий, но нужно решить архитектурный вопрос — `pet/`
сегодня НЕ импортирует `llm_gateway` вообще; чтобы это заработало,
`pet/`'s Python-процесс должен получить доступ к `llm_gateway`'s
конфигу/секрет-хранилищу того же узла (сейчас это два разных мира с
разным жизненным циклом процесса).

**PHASE 2 — места, где нужен адаптер (особый формат/логика)**
`pet/chat_local.py` — сложнее: есть тонкая, живо протестированная
логика системного промпта под конкретную модель (self-report тег,
"характер" помощника) и отдельный тест (`relationship_memory_regression_test.py`),
буквально проверяющий, что вызов идёт "ровно один раз в Ollama" —
миграция потребует переписать и этот тест, и живо проверить, что
другая модель через шлюз так же надёжно отдаёт нужный формат.
`agent/` эмбеддинги (`orch_registry_search.py`, `final_claim_coverage.py`,
`claim_relation.py` x2, плюс неверифицированный список из §2.3) —
нужен НОВЫЙ метод в `llm_gateway` (`embed()`), которого сегодня не
существует вообще — это не адаптер поверх существующего, а новая
абстракция с нуля, с собственным выбором бэкенда для эмбеддингов
(не факт, что тот же провайдер, что для генерации).

**PHASE 3 — тесты и mocks**
`client_regression_test.py:240-248,304-310` — тест, кодирующий именно
спорный тихий-фоллбэк контракт из §5 — при любом решении по §5 этот
тест придётся переписать осознанно, не просто починить.
`relationship_memory_regression_test.py` — придётся переписать под
новую реализацию `pet/chat_local.py`, если Фаза 2 состоится.
Остальные ~15 TEST_ONLY тестов в `agent/` — не требуют изменений
(исторические метки, не проверяют реальный Ollama-путь).

**PHASE 4 — startup/tooling/docs**
`README.md` — обновить формулировку про "YANDI Помощник = приватный
чат с локальной Ollama-моделью", если Фаза 2 меняет это на
модель-агностичный чат.
`start.sh` — уже корректен (warn, не блокирует), менять не обязательно.
`node/src/ai_rpc/*` — самая тяжёлая часть: либо (а) построить мост
Rust→Python к `llm_gateway.complete()` (IPC/локальный HTTP), либо (б)
реализовать в самом Rust параллельную backend-абстракцию (свой
llama.cpp биндинг + HTTP-клиенты к remote API), дублируя логику
`llm_gateway`. Оба варианта — architectural, не рефактор.

**PHASE 5 — Ollama становится опциональным backend'ом, не фундаментом**
Возможно только после закрытия Фаз 1-4. До этого момента удаление
Ollama с машины реально ломает: перевод/приватный чат/фоновую
валидацию в `pet/`, AI-RPC в `node/`, и определение противоречий между
утверждениями в `agent/`.

**Риски по этапам:** Фаза 1 — низкий (изолированные text-completion
вызовы). Фаза 2 — средний-высокий (эмбеддинги затрагивают ядро
эпистемики; `chat_local.py` затрагивает пользовательский UX,
завязанный на конкретную модель). Фаза 3 — низкий технически, но
требует осознанного решения по контракту §5 (это продуктовое решение,
не техническое). Фаза 4 — низкий для `README`/`start.sh`, **architectural**
для `node/`. Фаза 5 — зависит целиком от успеха 1-4.

================================================================================
8. FINAL VERDICT
================================================================================

**C. GATEWAY EXISTS BUT OLLAMA IS STILL A HIDDEN FOUNDATION.**

Обоснование фактами, не ощущением:

1. Шлюз реален, хорошо спроектирован и честно работает как единственная
   точка входа для генерации текста — но ТОЛЬКО внутри `agent/`.
2. Два целых соседних мира кода (`pet/` — то, чем реально пользуется
   человек; `node/` — транспортный слой сети) никогда не подключались
   к шлюзу и не знают о его существовании. Это не мелкие остаточные
   случаи — это полноценные, живые подсистемы.
3. Внутри самого `agent/` целый КЛАСС вызовов (эмбеддинги, ключевые для
   эпистемики — определение противоречий между утверждениями) никогда
   не был абстрагирован шлюзом вообще.
4. Даже там, где шлюз используется правильно и по всем канонам —
   найден и живо воспроизведён путь, где Ollama тихо подменяет явно
   настроенный владельцем backend при его сбое, и это поведение
   закреплено тестом как ожидаемое, а не забыто.
5. Сама идея "любая нода — любая модель" ограничена на уровне
   межнодового доверия: чужую ноду можно опросить-провалидировать
   только если она говорит на Ollama-протоколе.

Это не "B — в основном отвязано, есть остаточные зависимости", потому
что остаточное — это не мелкие хвосты, а полноценные подсистемы и
целый класс вызовов. Это не "A" — очевидно. Это не "D — неубедительно" —
все находки подтверждены построчным чтением кода и живым
воспроизведением, не догадкой.

**Главный вывод для мандата "доказать, что интеллект стал заменяемым
компонентом, а не переименованной зависимостью от Ollama":** внутри
`agent/` для генерации текста это уже почти правда — модель
действительно можно сменить, и нода не перестаёт быть той же нодой.
Но это правда только для одной из трёх реальных поверхностей системы.
Пока `pet/` и `node/` не подключены к тому же принципу, интеллект узла
в целом ещё не стал по-настоящему заменяемым — он стал заменяемым
только там, где это уже удобно было сделать.

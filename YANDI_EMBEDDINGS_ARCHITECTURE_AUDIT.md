4. EMBEDDING USE CASES
================================================================================

Семь РАЗНЫХ задач, использующих геометрию векторного пространства —
не путать друг с другом:

- **A. RAG-поиск по registry** — `orch_registry_search.py`.
- **B. Claim similarity / топическая близость** — ДВА независимых
  метода в одном файле (`claim_relation.py`): `classify_relation()`
  (nomic-embed-text) и `is_relevant()` (embeddinggemma) — разные модели
  для родственной задачи, без единого объяснения почему.
- **C. Contradiction/support prefilter перед LLM NLI** —
  `extract_claim_from_source()`.
- **D. Дедупликация убеждений** — `belief_manager._find_similar`
  (порог 0.70).
- **E. Semantic cache lookup** — `orch_cache.py` (порог 0.95,
  **персистентный** индекс).
- **F. Оценка качества источника** — `source_quality.py`.
- **G. Evidence↔claim mapping** — `claim_evidence_mapper.py`.
- **H. Маршрутизация кандидатов на NLI** — `final_claim_coverage.py`
  (не similarity-решение само по себе, а предфильтр "кого вообще
  сравнивать через дорогой LLM-вызов").

5. MODEL ASSUMPTIONS
================================================================================

- **Имя модели захардкожено буквальной строкой** в каждом из 10 мест
  (`"embeddinggemma:latest"` или `"nomic-embed-text:latest"`) — не
  конфигурируется, не читается из настроек узла.
- **Пороги similarity явно откалиброваны под конкретную модель:**
  - `is_relevant()`: порог ~0.43-0.45, в коде прямо написано "по
    измеренным данным: нерелевантное ~0.14-0.38, релевантное ~0.45-0.56"
    — эмпирическая калибровка под `embeddinggemma`.
  - `classify_relation()`: пороги 0.35/0.40/0.45/0.60 — под
    `nomic-embed-text`, без явного комментария о калибровке, но той же
    структуры.
  - `belief_manager._find_similar`: порог 0.70, под `embeddinggemma`.
  - `orch_cache.py`: порог 0.95 — самый высокий, под `nomic-embed-text`,
    и самый рискованный при смене модели (см. §6).
- **Размерность вектора нигде не проверяется явно** — известна только
  фактической длиной массива на диске (768 у обоих найденных
  персистентных хранилищ), программно не сверяется нигде из
  проверенного кода.
- **Формат ответа Ollama-эндпоинта используется по-разному**:
  `/api/embed` (новый, batch-способный) для `embeddinggemma`-вызовов,
  `/api/embeddings` (старый, по одному) для `nomic-embed-text`-вызовов
  — похоже на исторический артефакт (разные вызовы писались в разное
  время, копируя разные примеры), а не на осознанный выбор протокола.

================================================================================
6. VECTOR SPACE IDENTITY — можно ли сегодня сменить embedding-модель
   без смешивания несовместимых пространств?
================================================================================

**Нет, минимум в двух конкретных, доказанных фактом данных на диске
местах:**

1. **`registry/orch_index/{faiss.index, docs.pkl, version.txt}`**
   (RAG-поиск, `orch_registry_search.py` + `orch_cache.py`) —
   реальный, персистентный FAISS-индекс. `version.txt` содержит `"v1"`
   — это версия СХЕМЫ ДОКУМЕНТОВ, не версия embedding-модели. При смене
   модели: либо размерность не совпадёт с уже построенным индексом
   (падение при поиске), либо, что хуже, случайно совпадёт по
   размерности и будет тихо выдавать бессмысленные similarity-числа.

2. **`registry/orch_cache/{sem_index.pkl (9 записей), sem_index_v2.pkl
   (120 записей)}`** (семантический кэш ответов) — распаковано и
   проверено фактически: оба файла хранят сырые 768-мерные векторы
   прямо в поле `vec`, рядом с `answer`/`trust_level`/`claims`/
   `evidence`/`query`/`ts`. Поле `version` — фиксированная строка
   `"v1"` у ВСЕХ 120 записей второго файла (притом сам файл уже
   называется `_v2`) — это версия схемы кэша, не модели. **Ни в одной
   из 129 существующих записей нет ни имени embedding-модели, ни
   dimension-поля.** Порог 0.95 откалиброван под `nomic-embed-text` и
   не имеет обоснования для другой модели.

**Остальные пути (belief_manager, claim_evidence_mapper,
claim_evidence_retriever, source_quality, обе ветки claim_relation,
final_claim_coverage) структурно БЕЗОПАСНЫ в этом смысле** — они
пересчитывают embedding заново на КАЖДЫЙ вызов с ОБЕИХ сторон
сравнения, ничего не персистируют как вектор (в SQL сохраняется только
исходный текст) — при смене модели обе стороны сравнения будут
вычислены новой моделью одинаково, смешивания не происходит.

**Итог раздела:** риск смешивания пространств реален и локализован
именно там, где векторы ПЕРЕЖИВАЮТ один запрос — то есть ровно в тех
двух хранилищах, что используют `nomic-embed-text`. Пути на
`embeddinggemma` (transient recompute-every-time) от этого риска
свободны структурно, а не случайно.

8. FAILURE MATRIX
================================================================================

Ни один живой embedding-путь не роняет весь пайплайн при недоступности
эндпоинта — везде есть деградация, но РАЗНОГО типа:

| Тип деградации | Где |
|---|---|
| Честное исключение наружу | нигде — все 10 мест ловят исключение сами |
| Тихий пустой результат (`{}`/пустой `SearchResult`) | `orch_registry_search.py`, `final_claim_coverage.py` |
| Тихий `None` → альтернативная (лексическая) логика вместо векторной | `claim_relation.py` (оба метода) |
| Тихий `None` → семантический prefilter пропускается целиком | `belief_manager.py` |
| Тихий `None` → трактуется как cache-miss | `orch_cache.py` |
| Тихий нейтральный `0.0` вместо реальной оценки | `claim_evidence_retriever.py`, `source_quality.py` |
| Явно помеченный fallback-путь в коде | `claim_evidence_mapper.py` |
| Деградация в БЕЗОПАСНУЮ сторону (больше проверок, не меньше) | `final_claim_coverage.py` — спроектировано осторожно, достойно отдельного упоминания как хороший пример |

**Не обрабатывается явно нигде из проверенного:** несовпадение
размерности векторов при сравнении, NaN/Inf в векторе, batch,
вернувший меньше векторов, чем было текстов на входе. Это не
гипотетические сценарии — это ровно то, что произошло бы при
незамеченной смене модели (см. §6).

================================================================================
10. FUTURE GATEWAY REQUIREMENTS (только требования, без реализации)
================================================================================

Строго из фактов, ничего не придумано:

- **Явная настройка embedding-провайдера, отдельная от completion-
  провайдера** — код уже использует ДВЕ разные модели для разных задач
  внутри одной и той же кодовой базы, так что развязка провайдеров —
  не гипотеза на будущее, а уже фактически существующая (пусть и
  неявная, нигде не декларированная) реальность.
- **И single, и batch режимы** — оба реально используются (7 single +
  3 batch среди 10 мест).
- **Явные, не молчаливые сбои на уровне gateway** — но с сохранением
  ВОЗМОЖНОСТИ вызывающего кода самому решить, деградировать ли (как
  сейчас делают все 10 мест) — то есть `LLMError`-подобное исключение,
  а не тихий `None`/`0.0` НА УРОВНЕ САМОГО GATEWAY; текущая
  дисциплина "как деградировать" пусть остаётся решением каждого
  call-сайта, как сейчас, просто на честном фундаменте.
- **Vector-space fingerprint/версия провайдера, привязанная к каждому
  сохранённому вектору** — это не абстрактное пожелание, это прямое
  следствие §6: два реальных хранилища на диске СЕГОДНЯ не могут
  обнаружить смену модели. Будущий gateway должен как минимум отдавать
  вместе с вектором идентификатор (имя модели + версия/dimension),
  чтобы КОД ВЫЗЫВАЮЩЕЙ СТОРОНЫ (не обязательно сам gateway) мог решить,
  сохранять ли это клеймо рядом с вектором.
- **Отсутствие скрытого протокольного допущения** — сегодняшний код
  использует и `/api/embed`, и `/api/embeddings` по историческим
  причинам, не по архитектурному выбору; будущий `embed()` не должен
  наследовать это как "два равнозначных способа", один способ вызова
  для вызывающего кода, а какой реальный wire-protocol использовать —
  дело backend'а.
- **Никакого протаскивания через существующий `complete()`** —
  эмбеддинги семантически не являются генерацией текста и не должны
  притворяться ей ради переиспользования кода.

11. MIGRATION ORDER (только план)
================================================================================

**Этап 1 — безопасные, транзитные пути (без риска смешивания
пространств):** `belief_manager.py`, `claim_evidence_mapper.py`,
`claim_evidence_retriever.py`, `source_quality.py`, обе ветки
`claim_relation.py`, `final_claim_coverage.py`. Ничего не персистируют
как вектор — миграция на `llm_gateway.embed()` меняет только ТО, ЧЕРЕЗ
ЧТО вычисляется вектор, не структуру данных вокруг него. Риск
регрессии — низкий, но пороги similarity (§5) калибровались под
конкретную модель — при реальной смене провайдера их придётся
перекалибровать заново, это отдельная, не техническая, а
продуктовая/эмпирическая работа.

**Этап 2 — персистентные хранилища (реальный риск смешивания
пространств):** `orch_registry_search.py` + `orch_cache.py` (оба пишут
и читают `registry/orch_index/`, `registry/orch_cache/`). Здесь
миграция НЕ может быть просто "заменить вызов" — сначала нужно решить,
что делать с уже накопленными 129+ векторами без метки модели:
пересчитать заново (дорого, но чисто) или разметить задним числом как
"создано nomic-embed-text v?" и не трогать, пока явно не попросят
инвалидировать. Это решение — не техническое, а продуктовое, не
принимать его без отдельного мандата.

**Этап 3 — мёртвый код:** `agent/embeddings.py` +
`registry/dataset/embeddings/faiss.index` — удалить или оставить как
груз, отдельное решение владельца, не блокирует остальное.

**Этап 4 — тесты:** посвящённый проход по ~13 найденным тестам,
классификация, написание тестов для `llm_gateway.embed()` с нуля
(наследовать не от чего — `llm_gateway/` тестов на embeddings не имеет
вообще).

12. FINAL VERDICT

**B. EMBEDDINGS REQUIRE PROVIDER ABSTRACTION + VECTOR SPACE IDENTITY.**

Обоснование фактами: абстракция провайдера нужна, потому что код УЖЕ
де-факто использует два разных провайдера (embeddinggemma/nomic) для
разных задач, десятикратно продублировав один и тот же HTTP-паттерн
без единой точки входа. Идентичность векторного пространства нужна не
абстрактно "на будущее" — она нужна ПРЯМО СЕЙЧАС, потому что два
реальных хранилища на диске (129+ записей) физически не могут сегодня
обнаружить смену модели, а связанные с ними пороги similarity
эмпирически калибровались под ту модель, что стоит сейчас. Это не "C"
(глубоко привязано именно к Ollama) — код может звать любой HTTP-
эндпоинт, дело не в Ollama-специфике, а в отсутствии абстракции и
метаданных как таковых.
